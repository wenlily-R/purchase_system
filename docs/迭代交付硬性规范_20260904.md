# 迭代交付硬性规范（2026-09-04 定稿，所有改动必须遵守）

## 背景
反复出现"改新功能→老功能坏/消失"。根因=代码结构集中(2大文件共用公共逻辑) + 开发流程缺防呆(改公共底层不告知/不全量回归/无回滚/硬编码/覆盖丢失/复现BUG不入回归)。
本规范双管齐下，违反任何一条=不交付。

## 一、公共底层改动必须提前告知（禁止静默）
涉及以下公共逻辑的改动，动手前必须在交付说明里明确列出"会影响哪些原有模块 + 风险评估 + 验证方案"：
- 审批引擎(create_approvals/start_instances/finish_approvals/驳回/撤回)
- 钉钉推送(dt_send_todo/dt_start_instance/dt_build_form/模板码)
- 库存引擎(入库/出库/退库/盘点改库存的公共函数)
- 单据状态机(状态流转公共逻辑)
- 权限体系(can_manage_config/__pageAllowed/菜单)
- 单号生成(gen_no/gen_req_no)
- 前端公共函数(buildNav/sw/rnder/groupRnder/detailModal)

## 二、每次迭代必跑全套回归
交付前必须完整执行：
1. check_all.sh（后端check_code + 前端JS语法 + 39项全链路回归 + 公网链接）
2. 新增功能专项测试（本次需求逐条验收）
3. 输出测试结果：老功能全部正常才可部署
回归脚本 test_regression_v1197.py 覆盖：公网/询价外链/钉钉通知跳转/审批驳回/撤回/附件/用户管理/库存/退库/公告/前端引用。
缺覆盖的模块(分批验收/入库/出库/权限分岗/合同)后续补进回归脚本。

## 三、数据库改动兼容历史单据
- 加字段用幂等 ALTER(IF NOT EXISTS 风格)
- 改默认值/加约束：只对新单据生效，历史数据不追溯修改
- 涉及存量数据解读逻辑变化时：先备份→评估旧数据影响→给出旧数据处理方案
- 每次数据库结构改动前 cp data/purchase.db data/purchase.db.bak_YYYYMMDD_HHMMSS

## 四、审批节点/提醒规则配置化
- 新增审批环节优先走 approval_flow_config(系统设置可视化)，不写死在代码
- 新增钉钉提醒接收人/时机优先走系统设置
- 代码里硬编码的审批人/模板逐步迁移到配置

## 五、代码合并防覆盖丢失
- 大段修改前先 git diff 看清楚改动范围
- patch 时包含足够上下文锚点，防止误匹配相邻代码
- 每次功能点完成立即 git commit（小步提交），不攒大改
- 合并/替换后立即跑前端JS语法检查(防整块崩)+后端check_code

## 六、上线前备份+版本回滚
- 每次交付前：数据库备份(bak文件) + 确认当前 git 版本可回滚
- 部署后异常：git checkout 上个版本 tag + 恢复数据库备份
- 稳定版本打 tag：stable_YYYYMMDD

## 七、历史BUG复现处理
- 复现的BUG除修复外，必须输出根因
- 把该场景加入回归测试用例(append到test_regression_v1197.py或新建专项脚本)
- 防止同样问题第三次发生

## 八、禁止事项(红线)
1. 禁止静默修改公共底层逻辑
2. 禁止改完不跑回归就交付
3. 禁止改动历史单据/历史审批数据
4. 禁止跳过数据库备份
5. 禁止"拆东墙补西墙"式交付(改A坏B还交付)
