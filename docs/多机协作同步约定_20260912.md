# 多机协作同步约定（2026-09-12 立，三机共识）

背景（当天发生的事，写下来避免重演）：
- V11.289 的一些改动被**另一台机器并行 merge 覆盖**（V11.295 提交信息里已记录并重做）；
- 一次 `reset --hard` 让某台机器本地看到的提交号"消失"，被误判为"远端历史被强推"（实际远端提交都在、也未被 force）。

## 五条约定

1. **不 force push，不 reset 后强推。** 任何机器、任何脚本都不例外。
2. **先 `git pull --rebase` 再推**，各机保持线性历史 —— 比 merge 更不容易出现"同一文件里一方被整体取掉"。
3. **推完等 30–40 秒**让其它机器的守护把新提交追平，再开始下一轮改动。
4. **要动同一处（同一文件/同一函数）先在群里说一声**，不要直接覆盖对方的改动。
5. **守护脚本统一用仓库里的版本**，不要各机自己改一份（本仓库 `mac_deploy_watch.sh` / `deploy_watch_windows.sh` 都是 `git fetch` + `git pull --ff-only`，不含 reset/force；本地旧版若带 `reset --hard`，会让该机本地提交无声回退，请替换为仓库版）。

## 各机守护脚本现状（代码已核对）

| 脚本 | 作用 | 拉取方式 |
|---|---|---|
| `mac_deploy_watch.sh`（Mac 生产机） | 30 秒轮询 GitHub | `git pull --ff-only`；本地有未提交改动/未推送提交 → 跳过本轮 |
| `deploy_watch_windows.sh`（Windows） | 轮询 + 安全快进 | `git fetch` + `git pull --ff-only` |
| `app_watchdog.py` | 代码变化后自检并重启 Flask | 不碰 git |

## 附：怀疑"提交号/改动丢了"时的三步自查

```bash
git fetch origin main
git merge-base --is-ancestor <提交号> origin/main && echo 在历史里 || echo 不在
git reflog --date=iso | grep -E "reset:" | head        # 本机是否被 reset 过
git log --format=%s origin/main | grep -E "^V11\.29[0-9]" | sort | uniq -c   # 有无同主题重复提交(重打痕迹)
```

判断口径：提交号还在 `origin/main` 及其祖先里 = 没丢；本机 reflog 无 `reset:` = 本机没做过回退；无同主题重复提交 = 没有"重打一遍再推"的痕迹。三者都对上，就不要按"被强推"处理，先怀疑本地那台被 reset 过。

## 迁移（表结构）补充

`git pull` 后**必须**再跑一次迁移，顺序不能反：`python migrate_db.py`（Mac 用 `python3`，Windows 用 `.venv\Scripts\python.exe`）。跑完最后一行应为「完成: 新执行 N 个, 跳过 M 个」，**不含"失败"** 才算通过；该脚本幂等、执行前自动备份。
